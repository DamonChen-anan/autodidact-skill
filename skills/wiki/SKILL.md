# Wiki 管理 Skill

根据用户传入的命令参数执行对应的知识库管理动作。

---

## 命令路由

根据调用上下文中的指令判断要执行哪个命令（不依赖特定参数格式，理解意图即可）：

- 意图是**编译/整理知识库**，或传入了 `--files` 参数 → 执行【Wiki 编译】
- 意图是**审计/检查知识库**，或传入了 `check` 关键字 → 执行【知识审计】
  - 若同时传入了问题列表文件路径 → 完整审计（问题覆盖 + 结构审计）
  - 若未传入问题列表 → 纯结构审计
- 意图不明确 → 输出用法提示：
  ```
  用法：
    /wiki compile [--files f1.md,f2.md]        —— 将 raw/ 素材编译为 wiki/
    /wiki check [questions_file] [--round N]   —— 知识审计（有问题列表时做完整审计，否则只做结构审计）
  ```

---

## 【Wiki 编译】

**目标**：读取 raw/ 下的素材，按知识库规则，在 wiki/ 下生成或更新结构化文章。

**增量模式**：如果 `--files` 参数指定了文件列表，只处理这些文件；否则处理 raw/ 下全部文件。

**执行步骤**：

1. 读取 `outputs/research_state.json` 中的 `topic` 字段，了解知识库的主题和研究目标（用于判断哪些内容值得提炼、哪些偏题）。
2. 确定待处理文件：
   - 有 `--files f1.md,f2.md,...` → 只读取这些文件
   - 无 `--files` → 列出 raw/ 下所有文件
3. 逐一读取待处理文件，提取文件头部元数据：
   - `质量评分`：高/中/低
     - 若值为"待评估"（用户手动放入的文件），按"中"处理，在编译摘要中标注"⚠️ 待评估文件按中质量处理：<文件名>"
   - `关联问题`：触发这次检索的问题（若为"手动抓取"则无关联问题约束）
4. 识别所有主题，规划文章列表。按质量加权：
   - 高质量来源：充分提炼，细节保留
   - 中质量来源：提炼核心观点
   - 低质量来源：仅提取明确的事实性信息，忽略模糊表述
5. 创建或更新 `wiki/INDEX.md`：
   - 列出所有主题及其对应文件的链接
   - 每个条目附一句话描述
6. 为每个主题创建或更新 `wiki/<主题名>.md`：
   - 文件开头是一段摘要（2-4 句话）
   - 正文结构清晰，按逻辑分节
   - 用 `[[主题名]]` 格式链接相关主题
   - 标注素材来源（文件名）
   - 如果 wiki/ 中已有该文章，按以下规则合并：
     - **合并优先级**：质量评分高 > 低；时间戳新 > 旧；直接相关 > 间接相关
     - 新内容作为补充段落插入相关章节末尾，不破坏原有结构
     - 若新内容与原有观点存在明显矛盾，在冲突处添加 `> ⚠️ 待核实：[说明矛盾]` 标记，供下一轮 wiki check 发现
   - **slug 碰撞处理**：若新 raw 文件与已有文件 slug 相同但 URL 不同，在文件名末尾加 `-2`、`-3`，不跳过
7. 编译完成后，输出摘要并返回结构化结果：
   ```
   ## Wiki 编译完成
   - 新建文章：X 篇（列出文件名）
   - 更新文章：X 篇（列出文件名）
   - 新增主题：[主题A, 主题B, ...]
   - 待评估文件已按中质量处理，无需人工干预：[文件名列表]（若有）
   → Step 3 完成，继续执行 Step 4（知识审计）
   ```

**注意**：不要修改 raw/ 下的任何文件。

---

## 【知识审计】

**目标**：评估 wiki/ 的知识完备性，输出结构化审计报告，供下一轮 questioner 使用。

**两种模式**：
- **完整审计**（传入 `questions_file`）：问题覆盖判断 + 结构性审计，autodidact 研究循环的标准调用方式
- **纯结构审计**（不传 `questions_file`）：只做结构性审计，适合用户手动触发

**输入**：
- `questions_file`（可选）：问题列表 JSON 文件路径
- `--round N`：当前研究轮次，用于命名输出文件（默认取当前最新轮次）

**执行步骤**：

**第一阶段：问题覆盖判断**（仅完整审计模式）

1. 读取 `questions_file` 中的问题列表。
2. 读取 `wiki/INDEX.md` 及所有相关 wiki 文章。
3. 对每个问题逐一判断：
   - **resolved**：wiki 中有充分、具体的覆盖
   - **partial**：wiki 中有相关内容但不完整，标注具体缺口
   - **open**：wiki 中完全没有相关内容
4. 对 resolved 和 partial 的问题，生成简要回答（2-5 句话）。

**第二阶段：结构性审计**（两种模式都执行）

从以下四个维度审查 wiki/（完整审计模式下**不重复**第一阶段已发现的 partial/open 问题）：

**① 知识漏洞**
- 提到了某个概念/方法但没有展开解释（如"详见X"但X不存在）
- 结论缺乏支撑（如"通常认为…"但没有具体依据）
- 某个重要子话题完全没有覆盖

**② 矛盾与不一致**
- 不同文章对同一事实的描述是否冲突？
- 同一概念在不同地方的定义是否一致？

**③ 来源缺失**
- 哪些重要结论、数据、判断没有标注来源（raw/ 文件）？

**④ 结构问题**
- 悬空链接：`[[主题名]]` 引用的主题是否都有对应文件？
- INDEX 一致性：INDEX.md 与实际文件是否一一对应？

**第三阶段：合并输出**

将所有阶段结果写入 `outputs/rounds/round_<N>_check.md`：

```markdown
# 知识审计报告（第 N 轮）

## 一、问题覆盖情况（完整审计模式）

### 已解决（resolved）
### Q: <问题文本>
**回答**：...
**来源**：wiki/<文章名>.md

### 部分覆盖（partial）
### Q: <问题文本>
**已知**：...
**缺口**：...

### 未覆盖（open）
- <问题文本>

---

## 二、知识漏洞（需要检索补充）
- [漏洞描述]：来自 wiki/xxx.md，具体缺口是…

## 三、矛盾与不一致
- [描述]：wiki/A.md 说…，wiki/B.md 说…（无则填"无"）

## 四、来源缺失的结论
- [描述]：wiki/xxx.md 中"…"缺乏来源支撑（无则填"无"）

## 五、结构问题
- 悬空链接：...（无则填"无"）
- INDEX 不一致：...（无则填"无"）

---

## 审计摘要
- resolved: X 个 / partial: X 个 / open: X 个（完整审计模式）
- 知识漏洞：X 个
- 矛盾：X 个
- 来源缺失：X 个
- 建议下一轮重点方向：[方向1, 方向2, ...]
```

同时在对话中输出结构化状态供 autodidact 使用：
```
## 知识审计完成（第 N 轮）
- resolved: X 个 / partial: X 个 / open: X 个
- 知识漏洞：X 个
- 矛盾：X 个
- 来源缺失：X 个
- audit_issues_count: X （= 知识漏洞数 + partial 问题数，供 autodidact 判断终止条件）
- 报告：outputs/rounds/round_N_check.md
→ Step 4 完成，继续执行 Step 5（更新 research_state.json）
```

**注意**：审计要有深度，每个发现都要具体到"哪篇文章的哪个部分"，这样 questioner 才能据此生成有针对性的问题。不要修改 raw/ 或 wiki/ 下的任何文件。
